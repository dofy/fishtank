# PixiJS 原生背景与造景性能对照

这是初次迁移时的历史记录。后续网格合批、摆动计算与滤镜范围优化，以及本地默认入口切换，见 [写实优化复测](PIXI_OPTIMIZATION.md)。下文数字保留为迁移基线。

测试日期：2026-10-19。这是发布前本地 v1.6.0 实验入口的测量，保留为历史基线；不代表当前线上版本的性能。操作方法见 [对照说明](PIXI_LAB.md)，逐帧数据与完整统计见 [原始 JSON](PIXI_BENCHMARK_RAW.json)。

## 环境和方法

- Chrome 155 / macOS，WebGL 使用 `ANGLE Metal Renderer: Apple M5`，浏览器帧率上限约 75 FPS。
- 除额外的 starter 记录外，每组使用相同的 **12 条鱼、9 件造景**，黑夜模式，鱼体摆动开启。写实效果列注明是否开启新增水下滤镜；LCD 始终禁用彩色光晕和水波滤镜。
- 按 **Canvas → PixiJS → PixiJS → Canvas** 顺序独立绘制。每轮预热 90 帧，再采样 180 帧；每个渲染器合计 360 个有效 CPU / 帧间隔样本。
- 两边重放同一份内存快照，以固定时间步生成位置，并包含一致的鱼食、水花和灯光。不会修改存档或把示例鱼加入背包。
- JS 时间包含各自的绘制 / 提交命令；帧率来自实际帧间隔。PixiJS GPU 时间通过 `EXT_disjoint_timer_query_webgl2` 异步获取，禁止 `gl.finish()` 等阻塞计时。每组取得 358 个有效 GPU 样本；末尾尚未返回的 query 没有强行等待。
- GPU 时间只覆盖 PixiJS 提交的 GPU 工作；Canvas 的内部 GPU 耗时不可直接取得，**不能拿 Canvas JS 时间与 PixiJS GPU 时间比较**。

## 如何看待这些数字

**LCD 的 CPU 收益更明确。** 本轮三个场景的平均 JS 耗时降低约 77–82%。点阵背景不再逐格执行 Canvas 命令，造景也不再每帧做 Path2D 点采样。鱼形仍沿用小纹理采样更新，因此 PixiJS 的 P95 仍高于其中位数，尚未完全消除周期性开销。

**写实模式目前没有测出性能优势。** 小鱼缸即使关闭新增光纹，PixiJS 的 JS 提交耗时仍高于 Canvas；开启网格摆动和光纹则需要更多 CPU / GPU 工作。目前应把它视为视觉与渲染结构的升级，不能宣称迁移后一定更快。

大多数测试都接近约 75 FPS 的刷新上限。小屏 LCD 的帧率差异还受到调度与少量长帧影响；Canvas 某些轮次出现较长的单帧间隔，不能仅凭该次 FPS 差异推断实际手机的流畅度。

这是一台机器上的本地开发模式、一次 ABBA 测量，并未给出跨设备置信区间。小屏场景只是同一台 Mac 的 390×844 视口、DPR 2 模拟，**不是手机硬件测试**。帧率也不能替代耗电测量。真实手机、Safari、长期稳定性和正式打包后的结果仍需另测。

## 迁移后的边界

背景、水色、远礁、沙床、灯架、灯光、背景鱼群、气泡、18 件造景、鱼食与水花均已使用 PixiJS 原生图形或着色器。原生鱼缸不再调用 `Renderer.scene()` 上传整缸 Canvas。静态几何和有限动画帧可复用；渐变使用缓存的小纹理。

鱼体仍复用既有 Canvas 绘制函数生成小纹理，LCD 姿态最多每秒更新 8 次；界面肖像和繁育 / 合成结果弹窗也保留原来的 Canvas 渲染。两边美术的阴影、光照与动画细节并非逐像素一致，因此这些数字代表当前两种实现的实际开销，不能推广为所有 Canvas / PixiJS 项目的结论。
